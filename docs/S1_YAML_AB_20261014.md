# S1 YAML-only A/B experiment (2026-10-14)

This experiment changes only three scalar parameter paths from the canonical
`config/ugv_v1_livo.yaml` template. All four profiles enable
`diagnostics.ingest.enabled`; the two experimental factors are:

| Profile | `preprocess.filter_size_surf` | `runtime.image_admission_hz` |
| --- | ---: | ---: |
| B0 | 0.1 | 10 |
| B1 | 0.15 | 10 |
| B2 | 0.1 | 7.5 |
| B3 | 0.15 | 7.5 |

## Prepare profiles off the Jetson

Use one explicit temporary output directory. Generation does not require a ROS
environment and never writes the canonical source:

```bash
python3 scripts/s1_prepare_yaml_ab.py --output-dir /tmp/fast_livo2_s1_yaml_ab
```

The directory contains four full ROS 2 parameter YAML files and
`s1_yaml_ab_manifest.json`. The manifest records the source and generated-file
SHA256 sums, git HEAD, filenames, and effective experiment parameters. Running
the command again is idempotent. It fails closed if the source contract has
drifted, YAML keys are duplicated, or an existing output directory has different
or extra content.

## Jetson execution (operator action only)

Do not edit code, configuration, branches, or recordings on the live Jetson.
Copy one generated directory to a stable absolute path, verify its hashes against
the manifest, and use ROS 2 Humble with the Livox and `ws_ham_slam` overlays
sourced. Select Cyclone DDS before launching:

```bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
```

Run only one FAST-LIVO2 node and one profile at a time. Capture a separate log
for every B0/B1/B2/B3 run. For example, launch B0 with:

```bash
ros2 launch fast_livo s1_fast_golden.launch.py mode:=livo input_mode:=raw params_file:=/absolute/generated/s1_b0_ugv_v1_livo.yaml use_sim_time:=false use_rviz:=false 2>&1 | tee s1_b0.log
```

Substitute both the generated YAML filename and log filename for the B1, B2,
and B3 runs. In a second ROS 2 Humble terminal with the same overlays and RMW
implementation sourced, confirm the effective parameter before accepting a run:

```bash
ros2 param get /laserMapping diagnostics.ingest.enabled
```

The result must be `Boolean value is: True`. The existing
`diagnostics.ingest.enabled` flag publishes no `/diagnostics` topic. It emits
`RCLCPP_INFO` lines tagged `[ingest]` to the node log, including
`wall_stamp_age_s`, `queue_size`, `estimator_wall_age_s`, and visual snapshots.
Verify the captured log directly, for example:

```bash
grep -F '[ingest]' s1_b0.log
```

Preserve the distinct B0, B1, B2, and B3 logs with their run metadata. Keep RViz
off for the controlled runs; it may be launched later as an optional separate
visualization step.

## Recording protocol

Run every profile for **T > 30 minutes** under the same route, sensor setup,
startup procedure, and recording configuration. Run the first A/B pass with
RViz off to avoid a visualization-load confound. Preserve the original bags and
capture diagnostics, odometry/trajectory, relevant timing and resource metrics,
drop/admission counts, and the generated YAML plus manifest for every run.
Compare B0--B3 only after checking equal input duration and sensor coverage.
Do not make a performance claim without a 30-minute moving-UGV run for every
profile.

The generated full files retain the source sensor topics, calibration offsets,
LO/LIO-related settings, and dense/metric cloud publication flags. This script
does not generate or modify LO or LIO profiles.
